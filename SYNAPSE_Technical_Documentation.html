SECTION 1 — PROJECT OVERVIEW

1.1 What is SYNAPSE?

SYNAPSE is an enterprise-grade, artificial intelligence-powered classroom intelligence and automated attendance management platform. It transforms standard laptop webcams, classroom IP cameras, and CCTV surveillance streams into automated, verified biometric lecture attendance systems without requiring manual student roll-calls, sign-in sheets, or RFID card scanners.

Built on a modern decoupled architecture consisting of a FastAPI (Python 3.14) backend and a React 18 (TypeScript) single-page application, SYNAPSE integrates low-level computer vision, deep metric feature extraction, multi-object spatial tracking, and timetable-linked relational databases to record, audit, and analyze student academic presence in real time.

1.2 The Problem SYNAPSE Solves

Traditional academic attendance recording in higher education institutions suffers from systemic inefficiencies, security vulnerabilities, and data latency:

  • Instructional Time Loss: Conducting manual roll-calls for 60 to 120 students consumes between 10 and 15 minutes of an instructional hour (16% to 25% of total lecture time).
  • Proxy Attendance / Buddy Punching: In paper signature sheets or RFID smart-card systems, students frequently sign for absent peers or swipe multiple cards, falsifying institutional attendance.
  • Administrative Overhead & Error: Faculty members spend substantial hours manually entering attendance tallies from paper registers into enterprise ERPs, introducing data-entry errors.
  • Delayed Shortage Identification: Institutional attendance regulations typically require students to maintain ≥75% attendance to qualify for semester examinations. Under manual systems, students and departments only realize an attendance shortage during end-semester audits when corrective intervention is impossible.

1.3 Why Automated Face-Recognition-Based Attendance is Useful

Facial biometrics provides an inherent, non-transferable proof of physical presence. Unlike RFID cards or PIN codes—which verify what a person possesses—biometric recognition verifies who the person is. Passive camera-based recognition requires zero physical contact (hygienic and durable), operates instantaneously as students enter the lecture hall, and produces tamper-proof, time-stamped visual audit trails.

1.7 End-to-End System Workflow Lifecycle

From the moment a faculty member opens the application to attendance recording, the execution proceeds as follows:

  1. Authentication: Faculty enters credentials on /login; backend verifies Argon2id password hash and issues a signed HS256 JWT access token.
  2. Session Initialization: Faculty navigates to Live Webcam Attendance; selects Subject and Classroom (auto-detected if timetable matches active wall clock); backend creates/resumes an ACTIVE LectureSession and loads enrolled student templates into an in-memory RAM cache.
  3. Webcam Stream Acquisition: Frontend invokes navigator.mediaDevices.getUserMedia, binding the 1280x720 video feed to a mirrored HTML5 <video> element.
  4. Frame Sampling & Transmission: A non-overlapping capture loop samples frames at 640px JPEG format (~35 KB) and transmits them to POST /api/webcam/process-frame.
  5. Inference & Biometric Matching: Backend executes 0.5x HOG face detection, extracts 128-d dlib ResNet embeddings, and computes vectorized Euclidean distances against cached roster templates.
  6. Database Deduplication & Commit: Matches with distance ≤ 0.50 are checked against the session database; if not previously marked, an AttendanceRecord with status PRESENT and a RecognitionEvent are committed in SQLite.
  7. Real-Time HUD Feedback: Frontend receives bounding boxes and telemetry; an interpolated 60 FPS canvas loop renders hot-pink bounding boxes with full student names and green [✓ PRESENT] badges.

SECTION 3 — WHICH ML/DL MODEL IS USED?

CRITICAL DISTINCTION FOR LECTURER / VIVA DEFENSE: SYNAPSE uses Deep Metric Learning via a pre-trained Deep Residual Neural Network (ResNet-34). SYNAPSE DOES NOT train a neural network from scratch using student photographs, and does NOT use custom SVM, KNN, or Random Forest classification layers. Students are recognized using mathematical distance in a continuous 128-dimensional Euclidean metric space.

3.1 Detailed Answers to Core ML/DL Questions

1. Is SYNAPSE using Machine Learning, Deep Learning, or both?

SYNAPSE uses both:

  • Classical Machine Learning is utilized during the Face Detection stage via Histogram of Oriented Gradients (HOG) combined with a Linear Support Vector Machine (Linear SVM). It is also used during Metric Matching via nearest-neighbor Euclidean distance thresholding.
  • Deep Learning is utilized during the Face Embedding Extraction stage via a 34-layer Deep Residual Convolutional Neural Network (ResNet-34).

2. Which exact face-recognition model is implemented?

The model is dlib's ResNet-34 Deep Metric Face Recognition Network (Davis King, 2017), accessed via the face_recognition.face_encodings() Python interface. It is defined by the pre-trained model weights file dlib_face_recognition_resnet_model_v1.dat.

3. Is it a pre-trained model or trained from scratch?

It is an already pre-trained model. The model weights were pre-trained by Davis King on a massive curated dataset of approximately 3 million human faces compiled from FaceScrub and VGG-Face datasets.

4. What neural network architecture is it based on?

It is based on a Residual Network (ResNet-34) architecture. Unlike standard convolutional networks that suffer from vanishing gradients when depth exceeds 20 layers, ResNet incorporates skip connections (identity shortcut mappings) allowing gradients to flow unimpeded through all 34 layers:

\mathcal{F}(x) = ext{Residual Mapping}, \quad y = \mathcal{F}(x, \{W_i\}) + x

5. What is the role of dlib?

dlib is the high-performance C++ machine learning library containing the compiled neural network inference engine, the ResNet-34 architecture implementation, and the 68-point facial landmark shape predictor (shape_predictor_68_face_landmarks.dat) used to align detected faces before embedding extraction.

6. What is the role of the face_recognition Python library?

face_recognition (authored by Adam Geitgey) provides a Pythonic wrapper around dlib's C++ API. It handles image loading, coordinates transformations, invokes dlib's HOG detector and landmark aligner, and converts dlib's internal dlib::matrix<double, 128, 1> outputs into standard 64-bit NumPy arrays (np.ndarray of shape (128,)).

7. Is HOG used for face detection?

Yes. SYNAPSE explicitly sets model="hog" in all detection calls: face_recognition.face_locations(rgb_frame, model="hog") (see biometric_service.py:113, 127 and cv_engine.py:82, 101). HOG is chosen because it runs in ~32 ms on standard laptop CPUs without requiring dedicated CUDA GPUs.

8. Is a separate deep learning model used for face recognition?

Yes. The face detector (HOG + Linear SVM) only locates the bounding box coordinates $[x, y, w, h]$ of faces. A completely separate deep neural network (ResNet-34) processes the cropped, aligned face image to produce the 128-dimensional biometric embedding.

9. What does the model produce after processing a face?

The model produces a 128-dimensional vector of real numbers (floating-point values typically ranging between $-0.25$ and $+0.25$, with an overall Euclidean vector norm between $1.28$ and $1.51$).

10. Why are 128-dimensional face embeddings used?

128 dimensions represent an empirically proven balance established by Google's FaceNet research. 128 dimensions provide sufficient mathematical degrees of freedom to capture subtle invariant facial geometries (inter-ocular distance, nasal bridge slope, jaw curvature) while keeping vector comparison operations computationally trivial ($0.07 ext{ ms}$ for pairwise dot-products and norms in RAM).

11. Is there an additional classifier like SVM, KNN, or Random Forest?

NO. SYNAPSE does NOT fit or train an SVM, KNN, or Random Forest classifier on student identities. The system performs direct Euclidean distance comparison against stored reference vectors in continuous metric space. Adding an SVM would require retraining the entire classifier every time a new student enrolls.

12. Does SYNAPSE train a neural network using student photographs?

NO. SYNAPSE never computes backpropagation, gradient descent, loss functions, or weight updates on student photographs. The ResNet-34 weights remain completely frozen.

13. If there is no custom training, what happens during student enrollment?

During enrollment, SYNAPSE uses the frozen pre-trained network purely as a Deterministic Feature Extractor. The student's facial frames are passed forward through the network (inference only) to generate 128-d vectors. These vectors are aggregated via NumPy mean (np.mean) and stored as a static numerical template in SQLite.

3.3 How Deep Metric Learning and Triplet Loss Work

The underlying dlib ResNet-34 model was trained using Triplet Loss. During its original training, the network was fed three images simultaneously:

  1. Anchor ($A$): A photograph of Person X.
  2. Positive ($P$): A different photograph of the same Person X (different lighting or angle).
  3. Negative ($N$): A photograph of a different Person Y.

The loss function penalized the network if the anchor was not closer to the positive than to the negative by an enforcement margin $lpha$:

\mathcal{L}(A, P, N) = \max\left( \|f(A) - f(P)\|_2^2 - \|f(A) - f(N)\|_2^2 + lpha, \; 0 ight)

By minimizing this loss over 3 million faces, the network learned an internal representation of human faces where variations due to lighting, expression, and angle produce tiny distance shifts, while differences in identity produce large distance shifts.

SECTION 4 — HOW FACE ENROLLMENT WORKS

4.1 The Complete Enrollment Pipeline Step by Step

Biometric enrollment is the process of generating and storing a baseline identity profile for a newly admitted student. The complete workflow in SYNAPSE is implemented across StudentManagement.tsx (frontend) and biometric_service.py (backend):

  1. Student Profile Creation: The administrator enters the student's institutional metadata (Full Name, USN, Department, Semester, Section, Email).
  2. Webcam Video Capture: The faculty or admin clicks "Start Face Enrollment". The browser webcam streams for approximately 5 to 6 seconds, extracting 8 distinct candidate frames under varied subtle head orientations (frontal, slight left yaw, slight right yaw, slight upward pitch).
  3. Primary Face Localization: In biometric_enrollment_service.py:180-195 and biometric_service.py:180-195, if multiple faces appear in a candidate frame (e.g. background students), SYNAPSE computes an area-to-center proximity score:
    ext{Score} = rac{ ext{Bounding Box Area}}{\sqrt{(c_x - c_{x, ext{target}})^2 + (c_y - c_{y, ext{target}})^2} + 50.0}
    This ensures that only the primary candidate positioned directly inside the visual center guide is extracted.
  4. Laplacian Blur Variance Filtering: In cv_engine.py:44-63, each face crop is converted to grayscale, and the variance of its Laplacian operator is computed:
    ext{Var}( abla^2 I) = rac{1}{N} \sum_{x,y} \left( abla^2 I(x,y) - \overline{ abla^2 I} ight)^2
    Any frame where $ ext{Var}( abla^2 I) < 14.0$ is classified as blurry and discarded without aborting the entire enrollment session.
  5. Illumination / Exposure Adequacy Check: In cv_engine.py:49-54, the mean pixel intensity $\mu$ of the crop is checked. Frames with $\mu < 25$ (underexposed/dark) or $\mu > 240$ (direct glare/overexposed) are rejected.
  6. 128-d Feature Extraction: For each accepted frame, face_recognition.face_encodings(rgb_frame, [chosen_loc]) runs dlib's ResNet-34 forward inference, producing a raw 128-d vector.
  7. Pairwise Distance Matrix & Outlier Medoid Rejection: When $\ge 3$ candidate encodings are collected (biometric_service.py:221-238), SYNAPSE constructs a full pairwise Euclidean distance matrix $D_{i,j} = \|v_i - v_j\|_2$. It identifies the Medoid (the frame whose embedding has the smallest sum of distances to all other frames):
    ext{Medoid Index } m = rg\min_i \sum_{j=1}^k \|v_i - v_j\|_2
    Any frame with distance $\|v_i - v_m\|_2 > 0.45$ represents a momentary artifact (sneeze, occlusion, sudden motion blur) and is pruned out.
  8. NumPy Mean Aggregation (Reference Implementation Integrity): In biometric_service.py:241, the remaining valid encodings are aggregated using a pure arithmetic mean:
    \mathbf{v}_{ ext{template}} = rac{1}{K} \sum_{k=1}^K \mathbf{v}_k = ext{np.mean}( ext{valid\_encodings}, ext{axis}=0)
    CRITICAL ENGINEERING NOTE: SYNAPSE deliberately avoids dividing $\mathbf{v}_{ ext{template}}$ by its Euclidean norm $\|\mathbf{v}_{ ext{template}}\|_2$. Dividing by the norm forces the vector onto the unit hypersphere ($\|\mathbf{v}\| = 1.0$). In dlib's native feature space, raw embeddings have natural norms between $1.28$ and $1.51$. Dividing by the norm creates a mathematical scaling mismatch between stored templates and live query vectors, degrading recognition distance. Pure NumPy mean preserves exact metric compatibility!
  9. Reference Photograph Selection: The physical frame whose individual embedding is closest to $\mathbf{v}_{ ext{template}}$ is saved to disk at backend/storage/enrollments/student_enroll_{id}_{usn}_reference.jpg.
  10. Database Persistence: The 128 floating-point numbers are serialized into a JSON array string and inserted into the biometric_enrollments table.
  11. Thread-Safe Cache Hot Reload: biometric_service.refresh_cache(db) immediately reloads all active templates into RAM, allowing the student to be recognized in live attendance seconds after enrollment without restarting the backend.

4.2 Technical Terminology Glossary

  • Face Detection: The computer vision task of locating whether and where human faces exist in an image, outputting rectangular bounding box coordinates $[x, y, w, h]$.
  • Face Encoding / Embedding: The transformation of an image of a face into a compact vector of numbers (128 values) where mathematical distance corresponds to identity.
  • 128-Dimensional Vector: An array of 128 numbers that represents the position of a face as a single point in a high-dimensional mathematical space.
  • Normalization: Scaling a vector so its mathematical length equals 1.0. (As documented above, SYNAPSE preserves dlib's unconstrained metric space).
  • Euclidean Distance: The standard straight-line geometric distance between two points in multidimensional space.
  • Template Aggregation: Combining multiple facial representations from different frames into a single, highly robust average representation.
  • Biometric Enrollment: The initial registration phase where physical traits are converted into digital mathematical templates.

SECTION 5 — HOW LIVE FACE RECOGNITION WORKS

5.1 Sequential Live Recognition Pipeline

When a lecture session is active and a student walks into the webcam frame, the processing pipeline executes at sub-second speeds (~241 ms total latency):

  1. Webcam Hardware Acquisition: The browser requests 1280x720 video at 30 FPS. The video stream is mirrored horizontally with CSS scale-x-[-1] to provide a natural selfie view.
  2. Client-Side Downscale & Compression: An offscreen HTML5 <canvas> captures the current video frame and resizes it to 640 px width (aspect-ratio preserved, typically 640x360 or 640x480). It compresses the frame into a lightweight JPEG at quality 0.75 (~35 KB).
  3. Non-Overlapping Asynchronous Request: The frontend ensures no two frame requests are in flight simultaneously (isRequestInFlightRef). A new frame is transmitted to POST /api/webcam/process-frame only after the previous response returns.
  4. Server-Side Ingestion: FastAPI decodes the base64 JPEG into a 3-channel BGR NumPy array (np.ndarray of shape [H, W, 3]).
  5. 0.5x Inference Scaling (Sub-Second Optimization): In biometric_service.py:112 and cv_engine.py:81, the BGR frame is converted to RGB and downscaled by $0.5 imes$ (fx=0.5, fy=0.5) down to 320x240 pixels. This reduces pixel operations by $4 imes$, cutting HOG detection time from ~140 ms to ~32 ms.
  6. HOG Face Detection: face_recognition.face_locations(small_rgb, model="hog") detects all face rectangles $[t, r, b, l]$ in the downscaled image.
  7. Coordinate Upscaling: Bounding box coordinates are multiplied by 2 ($t imes 2, r imes 2, b imes 2, l imes 2$) to match the original 640px coordinate space.
  8. 128-d Embedding Extraction: face_recognition.face_encodings(small_rgb, small_locs) passes each aligned face through the dlib ResNet-34 network, returning 128-d query vectors.
  9. Vectorized In-Memory Cache Matching: In biometric_service.py:338, the live vector is compared against all pre-loaded student vectors in RAM:
    ext{face\_distances} = ext{face\_recognition.face\_distance}(\mathbf{V}_{ ext{cached}}, \mathbf{v}_{ ext{live}})
    Because all 23+ active templates reside in a contiguous NumPy array in RAM, this step completes in just 0.07 milliseconds.
  10. Tolerance Comparison & Decision: The minimum distance $d_{\min} = \min( ext{face\_distances})$ is found.
    • If $d_{\min} \le 0.50$, the student with index $rg\min$ is confirmed.
    • If $d_{\min} > 0.50$, the face is flagged as UNKNOWN.
  11. Ambiguity Protection Check: If the top two candidate matches belong to different students and their distance difference is $< 0.035$, SYNAPSE flags the detection as AMBIGUOUS to prevent false identity swaps.
  12. JSON Response Delivery: Backend returns bounding box coordinates, student name, USN, match status, and confidence percentage.
  13. Frontend HUD Smoothing & Mirror Reconciliation: The browser reconciles coordinates using the mirroring formula $x_{ ext{mirrored}} = W_{ ext{canvas}} - x - w$, interpolates positions at 60 FPS using Exponential Moving Average (EMA) damping, and draws the hot-pink box and [✓ PRESENT] badge.

SECTION 6 — HOW THE MODEL IDENTIFIES A STUDENT

6.1 Mathematical Principles of Euclidean Metric Space

The core of SYNAPSE's recognition engine is geometric rather than statistical classification. Each enrolled student is represented by a 128-dimensional point in Euclidean space $\mathbb{R}^{128}$:

\mathbf{u} = (u_1, u_2, \dots, u_{128}) \quad ext{and} \quad \mathbf{v} = (v_1, v_2, \dots, v_{128})

When a live query face $\mathbf{q}$ is detected, SYNAPSE computes the exact Euclidean Distance (also called the $L_2$ norm of the difference vector) between $\mathbf{q}$ and every enrolled template $\mathbf{u}_k$:

d(\mathbf{q}, \mathbf{u}_k) = \|\mathbf{q} - \mathbf{u}_k\|_2 = \sqrt{\sum_{i=1}^{128} (q_i - u_{k,i})^2}

6.2 Why Same Person Produces Small Distance, and Different People Produce Large Distance

  • Intra-Personal Variance: When the same student stands in front of the camera on different days (varying expressions, slight shadows, or different hairstyles), the deep residual layers project the face into nearly the identical cluster in $\mathbb{R}^{128}$. The Euclidean distance typically falls between $0.06$ and $0.38$.
  • Inter-Personal Variance: When two different students are compared, the distinct structural proportions of their facial bones, orbits, and jawline cause the ResNet to project them into distant geometric clusters. The Euclidean distance typically exceeds $0.65$ to $1.10$.

6.3 The Calibrated Recognition Threshold: Tolerance = 0.500

In biometric_service.py:27 and cv_engine.py:17, SYNAPSE enforces an operational threshold:

ext{Identity Decision} = egin{cases} ext{MATCH (Student } k^*), & ext{if } d_{\min} \le 0.500 \ ext{UNKNOWN (Reject)}, & ext{if } d_{\min} > 0.500 \end{cases} \quad ext{where } k^* = rg\min_k d(\mathbf{q}, \mathbf{u}_k)

A tolerance of $0.500$ was calibrated after exhaustive testing against the previous Smart Attendance project. While dlib's default academic benchmark is $0.60$, real-world classroom lighting can cause false positives at $0.60$. A threshold of $0.500$ provides strict imposter rejection (zero false acceptance) while maintaining a high true acceptance rate for enrolled students.

SECTION 7 — HOW AUTOMATIC ATTENDANCE IS MARKED

7.1 Four Distinct Computer Vision Operations

Examiners frequently ask students to distinguish between computer vision stages. In SYNAPSE, they represent four strictly separate architectural phases:

  1. Face Detection: "Where is a face?" Locates rectangular coordinates $[x, y, w, h]$ in pixel space using HOG + Linear SVM. Does not know or care who the face belongs to.
  2. Face Tracking: "Where did this face move?" Preserves identity continuity across consecutive video frames using spatial proximity and centroid tracking to prevent count jitter.
  3. Face Recognition: "Who is this face?" Converts the detected face crop into a 128-d vector via ResNet-34 and computes Euclidean distance against stored profiles.
  4. Attendance Marking: "Should this student's institutional record be updated?" A business logic operation that validates session timetable, checks academic roster enrollment, prevents duplicate database inserts, and records a verified PRESENT record with a timestamp.

7.3 Duplicate Attendance Prevention Mechanism

In a 60-minute lecture, a student remains in front of the camera for thousands of frames. Creating a database row on every frame would result in tens of thousands of duplicate records and crash report generation. SYNAPSE implements a strict Dual-Layer Deduplication Guard:

  1. In-Memory Session Cache (Zero-IO Layer): In webcam_attendance_manager.py:309-312, the active session maintains an in-memory set: session_state["attendance_marked_ids"] = set(). Before invoking database queries, the system checks: 
    is_new = student_id not in session_state["attendance_marked_ids"]
    If is_new is false, SYNAPSE bypasses database writes entirely.
  2. Database Unique Constraint (ACID Layer): In webcam_attendance_manager.py:323-328, SYNAPSE queries the relational table: 
    record = db.query(AttendanceRecord).filter(
    AttendanceRecord.session_id == session_id,
    AttendanceRecord.student_id == student_id
).first()
    If a record already exists, it only updates last_detected_at = now and increments observations_count += 1 without inserting duplicate rows.

SECTION 8 — CAMERA AND REAL-TIME PROCESSING

8.1 Client-Side Camera Optimization

Real-time browser-based computer vision requires balancing frame rate with network bandwidth and CPU inference load:

  • Horizontal Selfie Mirroring: Laptop webcams feel unnatural when unmirrored (raising your right hand moves the screen's left). In LiveWebcamAttendance.tsx, the <video> element is mirrored using CSS scale-x-[-1]. However, an unmirrored overlay canvas renders bounding boxes. To ensure bounding boxes match the student's physical face position, SYNAPSE applies the coordinate mirror formula:
    x_{ ext{mirrored}} = W_{ ext{canvas}} - x_{ ext{source}} - w_{ ext{box}}
  • 640px JPEG Downsampling: Instead of transmitting full 1080p raw frames (which exceed 4 MB and choke WebSocket/HTTP connections), the client draws the video to an internal canvas at 640px width and compresses it to JPEG at 0.75 quality (~35 KB). This cuts transmission time to ~15 ms.
  • Non-Overlapping Frame Dispatch: The client uses a strict lock (isRequestInFlightRef). If the backend is processing frame $N$, frame $N+1$ is never sent. As soon as frame $N$ returns, the client grabs the latest instant frame, preventing queuing latency (lag build-up).

8.2 60 FPS Bounding-Box Smoothing & Sticky PRESENT Status

Raw inference runs at ~4 FPS (every ~241 ms). If bounding boxes were only drawn when inference returns, the square would jump and jitter across the screen. SYNAPSE solves this using an independent 60 FPS requestAnimationFrame Interpolation Loop:

  • Exponential Moving Average (EMA) Damping: Current coordinates $[x_c, y_c]$ smoothly glide toward the latest target coordinates $[x_t, y_t]$ on every display refresh:
    x_c(t) = x_c(t-1) + lpha \cdot (x_t - x_c(t-1)), \quad lpha = 0.35
  • Sticky [✓ PRESENT] HUD Badge: Once a student is recognized, the track retains its status = "RECOGNIZED" and displays a prominent emerald/green badge reading [✓ PRESENT] attached directly to the top edge of the hot-pink face box. The track reconciler uses an extended stale decay timeout (1200 ms), ensuring that when a student settles into their seat, the bounding box remains smoothly locked to their face without flickering out.

SECTION 10 — SECURITY AND RELIABILITY

10.1 Authentication & Password Cryptography

  • Argon2id Password Hashing: In backend/app/auth.py:13-23, password hashing uses argon2.PasswordHasher(). Argon2id combines memory-hardness (preventing parallel ASIC cracking) with side-channel resistance, far exceeding legacy MD5 or SHA-256 hashes.
  • JWT Bearer Token Architecture: Authentic sessions receive a cryptographically signed JSON Web Token using the HS256 algorithm with a 24-hour expiration window. Protected endpoints invoke FastAPI's Depends(get_current_user) dependency to validate claims.
  • Role-Based Access Control (RBAC): Endpoints such as faculty creation, student deletion, and camera registry updates enforce the require_admin dependency (backend/app/auth.py:57-61), returning HTTP 403 Forbidden to faculty accounts.

10.2 Biometric Privacy & Data Protection

  • Irreversible Template Storage: SYNAPSE does NOT store raw video streams or high-resolution facial crops in database tables. The primary biometric identifier is the 128-dimensional floating point embedding. Deep metric embeddings are mathematical dimensionality reductions ($921,600 ext{ bytes} o 128 ext{ floats}$); reconstructive inversion back to a photorealistic human face is non-trivial and effectively irreversible.
  • Audit Trails for Data Access: Every enrollment and attendance marking action logs the initiating user's email, IP address, and record ID into the immutable audit_logs table.

10.3 Honest Security Limitations

ACADEMIC HONESTY & LIMITATIONS:
  • 2D Presentation Attack Vulnerability (Photo Spoofing): Because standard laptop webcams capture RGB images without infrared illumination or 3D depth sensors, a student could theoretically hold up a printed color photograph or smartphone screen displaying an enrolled student's face. True anti-spoofing requires active challenge-response (blink/smile detection) or structured-light depth cameras (Intel RealSense).
  • Client-Side HTTPS: In local development, the camera operates over http://localhost:5173 (which browser security permits for localhost). Production deployment across a campus network strictly requires HTTPS TLS certificates; modern browsers block getUserMedia camera permissions over unencrypted HTTP.

SECTION 12 — LIMITATIONS AND FUTURE IMPROVEMENTS

12.1 Real-World Technical Limitations

  1. Extreme Pose & Profile Angles (>30° Yaw/Pitch): HOG detectors are frontal detectors. If a student turns their head more than 30 degrees away from the lens (looking at their neighbor), HOG detection fails to localize the bounding box.
  2. Severe Low-Light / Backlit Glare: Poor ambient lighting decreases contrast, causing Laplacian variance to drop below 14.0, which triggers quality rejection.
  3. Single-Threaded CPU dlib Inference: In CPU mode, ResNet-34 inference takes ~200 ms per face. If 5 students appear in the frame simultaneously, sequential CPU inference scales to $5 imes 200 ext{ ms} pprox 1000 ext{ ms}$ (1 FPS).
  4. 2D Static Presentation Attacks: Absence of hardware infrared / depth sensing allows potential photograph spoofing.

12.2 Proposed Future Engineering Roadmap

  • Blink & Micro-Expression Liveness Detection: Implementing eye aspect ratio (EAR) analysis over temporal video frames to require natural human blinking before committing attendance.
  • ONNX Runtime & TensorRT GPU Acceleration: Exporting the ResNet-34 model to ONNX and compiling with NVIDIA TensorRT to achieve 15 ms inference latency, enabling 60 FPS real-time multi-student concurrency.
  • Multi-Camera IP Surveillance Ingestion: Adding multi-threaded RTSP demuxers to simultaneously ingest ceiling dome cameras and podium webcams across lecture halls.

SECTION 13 — QUESTIONS A LECTURER MAY ASK (35 VIVA Q&A)

These 35 questions and answers are structured specifically for university examiners and lecturers, written in direct, technically rigorous, and speakable language:

Q1. What is face recognition?
Answer: Face recognition is a computer vision biometric technology that mathematically compares features from a captured facial image against a database of known identity templates to verify or determine a person's physical identity.
Q2. What is the fundamental difference between face detection and face recognition?
Answer: Face detection only answers "Where is a face located in this image?" by returning rectangular bounding box coordinates $[x, y, w, h]$. It does not identify who the face is. Face recognition answers "Whose face is this?" by extracting unique mathematical features and matching them against stored identity templates.
Q3. Which machine learning or deep learning model is used in SYNAPSE?
Answer: SYNAPSE uses dlib's pre-trained ResNet-34 Deep Metric Face Recognition Network (Davis King, 2017) accessed through the face_recognition library. It is a 34-layer deep residual neural network trained on 3 million faces using Triplet Loss.
Q4. Have you trained your own neural network from scratch?
Answer: No, we have not. Training a deep face recognition network from scratch requires millions of labeled facial images, weeks of multi-GPU compute, and millions of parameters. Instead, SYNAPSE utilizes the proven industry approach of Deep Metric Learning with pre-trained weights, using the network as a frozen feature extractor.
Q5. If you haven't trained a model, how does the system learn to identify college students?
Answer: The system does not need weight training to identify students. The pre-trained ResNet-34 has already learned the universal geometric features of human faces. During enrollment, the network maps a student's webcam frames into a 128-dimensional Euclidean space. The resulting average vector is saved in our database. Live recognition simply calculates the Euclidean distance between a live face's vector and these stored templates.
Q6. What is a pre-trained model?
Answer: A pre-trained model is a neural network whose weights and layer filters have already been trained and optimized on a large benchmark dataset by researchers, allowing others to reuse its learned feature extraction capabilities without repeating the expensive training process.
Q7. What is a Convolutional Neural Network (CNN)?
Answer: A CNN is a deep learning architecture that uses spatial convolution filters (kernels) to automatically extract hierarchical visual patterns from images—starting from simple edges and textures in early layers to complex facial structures in deeper layers.
Q8. What is a Residual Network (ResNet), and why is it better than a standard CNN?
Answer: ResNet introduces skip connections (identity shortcuts) that allow gradients to pass directly through layers without attenuation. Standard deep CNNs suffer from vanishing gradients when layers exceed 20, causing training degradation. ResNet-34 allows all 34 layers to train effectively, capturing much richer facial representations.
Q9. What is HOG (Histogram of Oriented Gradients)?
Answer: HOG is a classical computer vision feature descriptor that counts occurrences of gradient orientation (edge directions) in localized portions of an image. It captures facial contours independently of illumination changes and runs extremely fast on commodity CPUs (~32 ms).
Q10. Why is dlib used in this project?
Answer: dlib is an optimized C++ scientific toolkit that provides high-performance implementations of the 68-point facial landmark shape predictor and the ResNet-34 metric feature extractor, enabling reliable sub-second face processing on standard laptops.
Q11. What is a face embedding?
Answer: A face embedding is a low-dimensional numerical representation of a face. It compresses thousands of image pixels into a vector of 128 continuous numbers where physical facial similarity directly correlates with geometric proximity.
Q12. Why are there exactly 128 dimensions in the embedding?
Answer: 128 dimensions is the mathematically validated benchmark established by Google's FaceNet and dlib. It provides enough degrees of freedom to uniquely differentiate millions of human identities while remaining small enough for instant in-memory vector comparison (0.07 ms for all students).
Q13. How does the system compare two faces?
Answer: By computing the Euclidean Distance between their 128-dimensional vectors: $d = \sqrt{\sum_{i=1}^{128} (q_i - u_i)^2}$. A small distance means the two faces belong to the same person; a large distance means they belong to different people.
Q14. What is Euclidean distance?
Answer: Euclidean distance is the straight-line geometric distance between two points in Euclidean space, calculated as the square root of the sum of squared differences across all 128 dimensions.
Q15. What is the recognition threshold in SYNAPSE?
Answer: The recognition threshold is 0.500. If the Euclidean distance between a live face and the closest enrolled student template is $\le 0.500$, the system accepts the identity. If it is $> 0.500$, the person is rejected as UNKNOWN.
Q16. What happens when an unknown or unregistered person appears?
Answer: The system computes distances against all enrolled templates. Because the person is unregistered, all distances exceed 0.500 (typically 0.65 to 1.10). The system flags the face as UNKNOWN, renders a yellow warning box, records zero attendance, and increments the unknown individual count in real-time telemetry.
Q17. Why do you capture multiple frames during biometric enrollment instead of a single photograph?
Answer: A single photograph is vulnerable to momentary shadows, slight head tilt, or motion blur. Capturing 8 frames over 5–6 seconds samples natural facial variations (yaw, pitch, expressions). Aggregating them via NumPy mean produces a robust consensus template that significantly improves live recognition accuracy under varied classroom angles.
Q18. How is attendance marked automatically in the database?
Answer: Once a face is recognized ($d \le 0.500$) and confirmed to belong to the active lecture's department and semester roster, SYNAPSE checks if the student was already marked. If not, it executes an atomic insert into attendance_records setting status = "PRESENT" with a timestamp and logs a RecognitionEvent.
Q19. How do you prevent duplicate attendance records when a student sits in front of the camera for an entire 1-hour lecture?
Answer: SYNAPSE uses a Dual-Layer Deduplication Guard: an in-memory set (attendance_marked_ids) that blocks redundant queries at zero CPU cost, and a database check (session_id + student_id) that only increments observation counts and updates last_detected_at without creating duplicate rows.
Q20. What happens if two enrolled students appear in front of the camera together?
Answer: The HOG detector localizes two distinct bounding boxes. The dlib encoder extracts two independent 128-d vectors. Vectorized matching identifies each student against the RAM template cache separately. Both students receive distinct bounding boxes and are both marked present without identity collision.
Q21. What is face tracking in this project?
Answer: Face tracking maintains identity continuity across consecutive video frames using spatial proximity and centroid matching. It ensures that moving faces maintain their track ID and prevents temporary background individuals from inflating the occupancy count.
Q22. How is real-time processing achieved on a laptop without a dedicated GPU?
Answer: Through four key optimizations: (1) client-side canvas downsampling to 640px JPEG; (2) server-side 0.5x scaling (320x240) for HOG detection; (3) in-memory RAM caching of all templates for 0.07 ms matching; and (4) a non-overlapping request loop that prevents network queue build-up.
Q23. What database is used and why?
Answer: SQLite with SQLAlchemy ORM. It is ACID-compliant, requires zero external server setup, supports strict foreign key constraints, and executes local queries in 1 to 3 milliseconds.
Q24. How is biometric information stored in the database?
Answer: Biometric vectors are serialized as JSON strings of 128 floating-point numbers in the embedding_data column of the biometric_enrollments table. Raw images are stored separately on disk, and only the file path is saved in the database.
Q25. What happens if the internet connection is lost during a lecture?
Answer: SYNAPSE runs 100% locally on the host machine (localhost). The FastAPI backend, SQLite database, and dlib AI models do not depend on external cloud APIs or internet connectivity. Attendance continues uninterrupted offline.
Q26. What are the limitations of the current implementation?
Answer: Key limitations are: (1) sensitivity to extreme face angles (>30° profile yaw); (2) vulnerability to 2D photograph spoofing without depth cameras; and (3) CPU bottlenecks when processing more than 5 faces simultaneously in a single frame.
Q27. How can the system be improved in the future?
Answer: By adding active liveness detection (blink and micro-movement analysis), compiling models to ONNX Runtime with TensorRT for GPU acceleration, and supporting multi-camera ceiling RTSP streams across large lecture halls.
Q28. What is the difference between Machine Learning and Deep Learning in this project?
Answer: Classical Machine Learning uses handcrafted feature algorithms (HOG edge gradients + Linear SVM) for face detection. Deep Learning uses automatic representation learning through deep layered neural networks (34-layer ResNet) to extract high-level semantic facial embeddings.
Q29. Is student enrollment supervised or unsupervised learning?
Answer: Enrollment is neither. It is deterministic feature extraction using a frozen model. The student's identity label is assigned by the administrator, and the model merely computes a mathematical projection without adjusting any weights.
Q30. Why did you choose Deep Metric Learning instead of training a custom CNN classifier with a Softmax layer?
Answer: A Softmax classifier has a fixed number of output classes ($N$ students). Every time a new student enrolls or drops out, the entire network must be retrained. Deep Metric Learning maps any face into an open-ended coordinate space, allowing instant onboarding of new students simply by storing their vector, with zero model retraining.
Q31. Why did you avoid dividing by the Euclidean norm during vector aggregation?
Answer: dlib's ResNet model outputs unnormalized vectors with natural lengths between 1.28 and 1.51. Dividing by the norm scales the vector to length 1.0, creating an artificial distance skew against live query vectors. Pure NumPy mean preserves the native metric space of the model.
Q32. What is the purpose of the Medoid outlier filter during enrollment?
Answer: If a student blinks, turns away, or sneezes during the 8-frame capture, that frame produces an outlier vector. The Medoid filter computes pairwise distances among all frames and discards any frame whose distance to the cluster medoid exceeds 0.45, ensuring only clean, consistent frames form the template.
Q33. What is the Ambiguity Check in SYNAPSE?
Answer: If a query face matches two different students within a tiny distance margin ($|d_1 - d_2| < 0.035$), SYNAPSE flags the result as AMBIGUOUS rather than guessing, routing the event to the verification queue to prevent accidental identity misassignment.
Q34. How does camera mirroring work without distorting bounding boxes?
Answer: The video preview is visually flipped using CSS scale-x-[-1]. To align bounding boxes on the unflipped overlay canvas, SYNAPSE applies the horizontal inversion formula $x_{ ext{mirrored}} = W_{ ext{canvas}} - x_{ ext{source}} - w_{ ext{box}}$, ensuring text and labels render left-to-right correctly over the student's face.
Q35. How does SYNAPSE protect password security and session integrity?
Answer: Passwords are protected using memory-hard Argon2id hashing with unique random salts. Sessions are secured via cryptographic HS256 JSON Web Tokens with a 24-hour expiry, enforced at the API level using role-based dependencies (require_admin).
